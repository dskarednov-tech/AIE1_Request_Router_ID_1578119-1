## Chapter I

На старте программы, в которой ты будешь собирать агентов, писать HTTP-клиентов и работать с векторными базами, важно сделать подготовительный шаг. Без него ты не сможешь ответить на главный вопрос: действительно ли LLM решает задачу лучше, чем простые правила? И стоит ли её сложность потраченных денег и времени?

Представь, что команде поддержки приходится ежедневно обрабатывать сообщения пользователей и понимать, о чем они просят. Одни обращения легко узнать с первого взгляда:

_«Не могу войти в личный кабинет»._

_«Платеж прошел, но деньги не появились на счете»._

_«После обновления перестал открываться отчет»._

Когда сообщений пять, их нетрудно разобрать вручную. Когда их сотни, команда поддержки тратит время на одно и то же действие: определить тему, понять срочность и передать обращение нужному специалисту.

Здесь может появиться идея сразу подключить языковую модель. Она умеет работать с текстом и выглядит естественным кандидатом для такой задачи. Но без понятной отправной точки невозможно ответить на важные вопросы: действительно ли модель распределяет обращения лучше, сколько стоят ее ошибки и оправдано ли усложнение системы.

В этом проекте ты создашь маршрутизатор обращений на явных правилах. В инженерной работе такую первую рабочую версию часто называют baseline - базой для последующего сравнения с более сложными системами. Она не поймет абсолютно любой текст, зато каждое ее решение можно объяснить найденным словом и конкретным правилом.

Твоя программа для команды поддержки будет:

- читать обращения из JSON- и CSV-файлов;
- определять категорию и приоритет каждого обращения;
- сохранять результат в понятном формате;
- понятно сообщать, если не сможет прочитать входные данные.

## Задание 1. Знакомство с данными

Любая система, которая принимает решение по данным, начинается не с кода, а со знакомства со входом и ожидаемым результатом. Иначе легко написать программу, которая работает аккуратно, но решает не ту задачу.

В `datasets/` находятся обращения в двух форматах. В `datasets/reference/routing-rules.md` записано, какие слова относятся к каждой категории и как определяется приоритет.

**Цель:** изучить входные данные, которые обрабатывает маршрутизатор, и ожидаемый результат его работы.

Что сделать:

1.  Запусти `python3 --version`. В ответе должна быть указана версия Python 3. Если команда не найдена, сначала настрой запуск Python в терминале и только потом продолжай.
2.  Открой `datasets/requests.json`. Убедись, что файл содержит массив обращений, а в каждой записи есть id и text.
3.  Открой `datasets/requests.csv`. Найди те же поля в строке заголовков и сравни одну CSV-строку с одной JSON-записью.
4.  Прочитай `datasets/reference/routing-rules.md`. Для каждой категории найди хотя бы одно подходящее обращение в JSON или CSV и проверь, какое правило приоритета к нему относится.
5.  Открой `datasets/expected-results.json`. Выбери несколько id, найди исходные обращения и пройди путь от текста через правило к ожидаемым category и priority.
6.  Создай `src/README.md`. Опиши назначение программы, требование использовать Python 3, поддерживаемые форматы JSON и CSV, а также поля id, category и priority в результате. Команды запуска ты добавишь позже, когда программа будет готова.

Например, запись `r-001` содержит слова «войти» и «пароля». По справочнику первое совпадение дает категорию access. Признаков high в тексте нет, поэтому для категории access получается приоритет medium. В `expected-results.json` у записи `r-001` должны стоять именно эти значения.

**Результат:**

В репозитории находится `src/README.md`, по которому можно понять назначение программы, требования к окружению, входные форматы и поля результата.

## Задание 2. Один вид для JSON и CSV

JSON и CSV выглядят по-разному, но в этом проекте содержат одни и те же сущности - обращения с идентификатором и текстом. Если сразу привести их к одной внутренней структуре, правилам маршрутизации больше не придется знать, из какого файла пришли данные.

Для внутреннего представления подойдет список словарей. Каждый словарь будет описывать одно обращение и содержать два поля: id и text.

Форма такой структуры на одной сокращенной записи выглядит так:

```json
[
    {
        "id": "r-001",
        "text": "Не могу войти в личный кабинет"
    }
]
```

Это пример результата чтения, а не готовая реализация функции.

**Цель:** научить программу читать JSON и CSV и приводить записи из обоих форматов к одному виду.

Что сделать в `src/main.py`:

1.  Создай функцию чтения JSON. Она получает путь к файлу и возвращает записи из корневого массива.
2.  Создай отдельную функцию чтения CSV. Используй строку заголовков, чтобы получить словарь для каждой строки. Для этого подойдет `csv.DictReader`, но можешь выбрать другой способ из стандартной библиотеки.
3.  Приведи каждую прочитанную запись к словарю с полями `id` и `text`. Значения преобразуй в строки и убери пробелы по краям.
4.  Проверь оба обязательных поля после очистки. Если `id` или `text` отсутствует либо остается пустым, прекрати обработку с ошибкой. Понятное сообщение для пользователя ты добавишь в задании 4.
5.  Добавь общую функцию выбора чтения. Она получает путь, смотрит на расширение `.json` или `.csv` и вызывает соответствующую функцию.
6.  Временно выведи результат чтения каждого корректного файла и посмотри на первую запись. В обоих случаях это должен быть список словарей с непустыми строковыми `id` и `text`. После проверки убери временный вывод.

Например, после очистки запись

`{"id": 42, "text": " Не работает отчет "}`

должна принять вид

`{"id": "42", "text": "Не работает отчет"}`

Для этого задания достаточно модулей json и csv из стандартной библиотеки.

**Проверь себя:** функции чтения работают независимо от маршрутизации и возвращают одинаковую по форме структуру. В коде не осталось временного `print`, добавленного только для проверки.

**Результат:**

В `src/main.py` находятся отдельные функции чтения JSON и CSV и общий выбор способа чтения. Оба корректных файла превращаются в список записей с непустыми строковыми `id` и `text`.

## Задание 3. Правила маршрутизации

Теперь программа умеет читать обращения независимо от формата файла, но пока не принимает решений. Следующий шаг - перевести правила из `datasets/reference/routing-rules.md` в код.

Порядок правил здесь важен. В одном сообщении могут встретиться признаки нескольких категорий, поэтому маршрутизатор выбирает первое совпадение из справочника. Важно учесть и обычную особенность русского текста: слова «счет» и «счёт» должны приводить к одному результату.

Разберем запись `r-003`:

>Дважды списалась оплата за тариф
>
>    ↓ нормализация
>
>дважды списалась оплата за тариф
>
>    ↓ первое совпадение по справочнику
>
>category = billing
>
>    ↓ признаков high нет, category не access и не bug
>
>priority = low

Твоя программа должна повторить этот путь для каждой записи, а не хранить готовый ответ для конкретного `id`.

**Цель:** определить категорию и приоритет обращения с помощью отдельных функций.

Что сделать:

1.  Перед поиском ключевых слов нормализуй текст: приведи его к нижнему регистру и замени ё на е. Все дальнейшие проверки выполняй на нормализованном тексте.
2.  Создай функцию определения `category`. Проверь категории в том порядке, в котором они записаны в `datasets/reference/routing-rules.md`, и верни первую найденную. Если совпадений нет, верни `other`.
3.  Создай отдельную функцию определения `priority`. Сначала проверь признаки `high`, затем правила для категорий access и `bug`; во всех остальных случаях верни `low`.
4.  Создай функцию маршрутизации одной записи. Передай ей словарь с `id` и `text`; в ответ получи словарь с `id`, `category` и `priority`.
5.  Передай функции маршрутизации все прочитанные записи по очереди и собери результаты в список.
6.  Сравни полученные `category` и `priority` с `datasets/expected-results.json`. Сопоставляй записи по `id`, потому что порядок объектов в массиве не оценивается. Если значение отличается, пройди путь этой записи по правилам так же, как в примере выше.

**Результат:**

В `src/main.py` находятся отдельные функции определения категории, приоритета и маршрутизации одной записи. Для обоих корректных наборов значения `category` и `priority` совпадают с ожидаемыми по `id`.

## Задание 4. Запуск из терминала

Пока функции можно вызвать только из кода. Но другой человек не должен открывать `main.py` и менять пути к файлам каждый раз, когда хочет обработать новый набор обращений.

Для этого программе нужен интерфейс командной строки (CLI). Пользователь запускает одну команду и передает ей путь к исходным данным и место для результата:

`python3 src/main.py --input src/data/requests.json --output src/result.json`

Здесь `--input` указывает, какой файл прочитать, а `--output` - куда сохранить итоговый JSON. Пути должны браться из команды, поэтому для нового файла не придется менять `main.py`.

У каждой команды есть код завершения. Код 0 сообщает терминалу, что все прошло успешно. Ненулевой код означает, что программа встретила ошибку и не смогла получить ожидаемый результат.

Если исключение осталось необработанным, Python выводит длинную цепочку вызовов - `traceback`. Разработчику она помогает искать дефект, но пользователю, который просто передал неверный путь или поврежденный файл, нужно короткое и понятное сообщение.

**Цель:** собрать функции в программу, которую можно запустить из терминала без изменения кода.

Что сделать:

1.  Добавь обязательные аргументы `--input` и `--output`. Можешь использовать стандартный модуль argparse.
2.  Настрой справку так, чтобы команда `python3 src/main.py --help` завершалась без ошибки и объясняла назначение обоих аргументов.
3.  Собери основной сценарий в таком порядке: прочитать файл из `--input` → маршрутизировать все записи → сохранить список по пути `--output`.
4.  При успешном запуске сохрани валидный JSON-массив и заверши программу с кодом 0.
5.  Проверь и обработай три ошибочных входа:
    - путь к входному файлу не существует;
    - JSON синтаксически поврежден;
    - в записи отсутствует или пусто поле `id` либо `text`.
6.  Для каждого ошибочного входа выведи короткое понятное сообщение, не показывай необработанный traceback и заверши программу с ненулевым кодом.
7.  Запусти программу с `datasets/requests.json` и сохрани результат в `src/result.json`. Открой файл и убедись, что внутри находится JSON-массив с полями `id`, `category` и `priority`.
8.  Вернись в `src/README.md` и добавь команды, которые ты фактически проверил: вызов `--help`, обработку JSON, обработку CSV и сохранение результата.

Не разбирай строку аргументов вручную через `split`: эту работу уже умеет выполнять `argparse`.

Поведение при ошибке может выглядеть так:

`$ python3 src/main.py --input /tmp/router-file-that-does-not-exist.json --output /tmp/router-result.json`

Ошибка: входной файл не найден

```bash
$ echo $?

1
```

Самостоятельно выбери текст сообщения и конкретный ненулевой код. Важно, чтобы пользователь понял причину, а `traceback` не появился. Команда `echo $?` показывает код завершения предыдущей команды в `bash` и `zsh`.

**Проверь себя:** `--help` и корректный вход завершаются с кодом 0; каждый из трех ошибочных входов завершается с ненулевым кодом и понятным сообщением.

**Результат:**

В репозитории находятся:

1.  `src/main.py` с командой запуска, сохранением JSON и обработкой трех ожидаемых ошибок;
2.  `src/result.json`, созданный из `datasets/requests.json`;
3.  `src/README.md` с командами, которые можно повторить без изменения кода.

## Задание 5. Проверка перед передачей

Рабочий запуск на одном файле еще не означает, что программа готова к передаче. Перед этим инженер повторяет основные сценарии и отдельно проверяет ситуации, в которых пользователь ошибся с файлом или данными.

Сейчас ты проведешь ручную приемку и оставишь результаты так, чтобы твои коллеги могли повторить те же команды.

**Цель:** проверить успешные и ошибочные сценарии и записать фактическое поведение программы.

В таблице ожидаемый результат записывается до запуска, а фактический - после. Статус `PASS` означает, что они совпали; `FAIL` означает, что найдено расхождение.

Строка для корректного JSON перед запуском может выглядеть так:
